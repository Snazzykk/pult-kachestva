# Пульт качества

**Пульт качества** — локальный дашборд зрелости тест-фундамента проекта. Отвечает на
вопрос, который обычно висит в воздухе на любом ретро или разговоре с руководством:
*«у нас с качеством всё нормально?»* — не ощущением, а цифрой, выведенной из фактов,
которые ты сам внёс: какие практики выстроены, что покрыто тестами, а что нет, какие
риски открыты, готов ли конкретный релиз к выкатке.

Не CI-плагин и не система метрик, которая сама что-то парсит. Это **чек-лист с
памятью**: ты один раз описываешь свой проект (сервисы, практики, риски), инструмент
на лету считает из этого зрелость по 8 областям, покрытие тестами по риску (а не по
количеству тестов), готовность к релизу, роадмап «что чинить в первую очередь» и тренд
по спринтам — и объясняет всё это языком, который понятен не только QA, но и бизнесу
(ROI автоматизации, время до обратной связи, сэкономленные часы).

## Зачем это

- **Навести порядок в голове.** Вместо смутного «у нас процессы так себе» — 8 областей
  с уровнем 0–4 и понятной шкалой (нет → ad hoc → систематизировано → в CI с метриками →
  самоподдерживается). Видно, что уже сделано, а что реально мешает двигаться дальше —
  и в каком порядке это чинить (зависимости между практиками учтены).
- **Не тестировать всё подряд.** Покрытие считается не «сколько тестов написано», а
  по риску: `Impact × Frequency` на каждую фичу каждого сервиса. Дыра в критичной фиче
  видна сразу, а десять автотестов на редко используемую мелочь не создают иллюзию
  порядка.
- **Не забыть чек-лист перед релизом.** Отдельная вкладка «Релиз»: состав релиза,
  автоматические сигналы риска («критичная фича без тестов», «flaky выше 5%») и
  редактируемый чек-лист готовности с тремя состояниями на пункт.
- **Показать прогресс, не рассказать про него.** Снапшот после каждого спринта — и
  тренд зрелости, покрытия и flakiness виден на графике, а не в переписке.
- **Ничего никуда не утекает.** Данные — это один YAML-файл на твоём диске. Никакого
  сервера, аккаунта, облака или телеметрии — см. [«Конфиденциальность»](#конфиденциальность).

## Быстрый старт

Требования: **Python 3.9+**, больше ничего не нужно для работы. `PyYAML` подхватится
сам, если он установлен (`python -m pip install pyyaml`) — тогда чтение файла чуть
устойчивее к ручным правкам, но и без него всё работает (свой минимальный YAML-парсер
в комплекте).

```bash
python run.py
```

Откроется браузер на `http://127.0.0.1:7842`. Пока своего файла нет — показывается
демо-пример компании «Snazzy» (с баннером-подсказкой сверху, что это демо), как
только что-нибудь поменяешь — рядом создаётся `data/quality-state.yml`, и дальше
редактируешь уже его.

Чтобы начать с нуля по своему реальному проекту: нижняя панель → **«🧹 Очистить и
начать заново»** (та же кнопка есть в баннере над демо-данными). Сотрёт демо-сервисы,
риски, карту, тренд и готовность к релизу, уровни практик обнулит в L0; сам каркас
10 встроенных практик и их целевые уровни останутся, имя компании тоже сохранится —
дальше просто переименуй. Предыдущая версия файла всегда остаётся рядом как `.bak`.

Свой рабочий файл лучше держать отдельно от кода инструмента (в этой папке может
жить конфиденциальная информация о сервисах компании, а `data/` в репозитории —
просто дефолт для быстрого старта):

```bash
python run.py --file "C:/work/qa-state/quality-state.yml"
python run.py --port 8000 --no-browser
```

По умолчанию сервер слушает только `127.0.0.1` (сам компьютер) и работает без
авторизации — это осознанный выбор для локального однопользовательского инструмента.
Не меняй `--host`, если не понимаешь, что тем самым открываешь чтение и запись
`quality-state.yml` любому в этой же сети.

### Показать команде или менеджеру

```bash
python build.py           # data/quality-state.yml  →  dist/pult.html
python build.py --file "C:/work/qa-state/quality-state.yml" --out report.html
```

`dist/pult.html` — самодостаточный файл с вшитыми данными на момент сборки:
открывается двойным кликом, работает без сервера и без Python, данные в нём
read-only (это снимок, а не рабочая копия). Его можно приложить к письму, положить
в Confluence или на сетевой диск.

## Модель оценки

Состоит из двух уровней: **практики** (как в принципе работает команда — общее на
весь проект) и **сервисы** (что конкретно покрыто тестами — своё у каждого сервиса,
внутри — фичи с оценкой риска).

### Практики — зрелость процессов, 0–4

По умолчанию 10 встроенных областей:

| id | Область | Что оцениваем |
|----|---------|---------------|
| `process`   | Процесс и Dev-QA Sync | когда подключается QA, DoD/DoR, ревью тест-артефактов |
| `env`       | Тестовые окружения | стабильность, доступность, локальный подъём, эфемерность |
| `framework` | Автофреймворк | слои, параллельный прогон, отчётность, фабрики данных |
| `gate`      | CI / Quality Gate + Fail Fast | тесты на PR, блокировка мёржа, остановка конвейера |
| `bugs`      | Баг-процесс | единый регламент, severity, триаж, метрики утечки в прод |
| `testdata`  | Тестовые данные | генерация, изоляция между тестами, очистка |
| `reporting` | Прозрачность и отчётность | таблица покрытия, снапшоты, регулярный отчёт с ROI |
| `nonfunc`   | Нефункциональное / нагрузка | перф, security, устойчивость |
| `requirements` | Требования и критерии приёмки | где живут, есть ли DoR, трассировка требование → кейс → тест |
| `observability` | Прод: наблюдаемость и инциденты | мониторинг, алерты, синтетика, разбор P1 |

Общая шкала уровней (детальные формулировки под каждую область — прямо в интерфейсе,
по клику на карточку практики):

- **L0** — нет / хаос
- **L1** — начальный, ad hoc, держится на одном человеке
- **L2** — систематизировано, но вручную
- **L3** — автоматизировано, встроено в CI, есть метрики
- **L4** — самоподдерживается: тренды, предиктивность, почти не требует ручного контроля

У каждой практики свой **текущий** и **целевой** уровень (цель не всегда L4 — не для
каждой области нужен максимум). Некоторые практики блокируют другие (`blockedBy`):
например, автоматизированный Quality Gate бессмысленно поднимать, пока фреймворк на
L0 — такие блокировки видно прямо на карточке и они двигают приоритет в роадмапе.

**Практики можно заводить свои.** «✎» на карточке — переименовать практику и
переписать формулировки уровней L0–L4 (можно и для встроенных, если дефолтная
формулировка не подходит под специфику проекта). Кнопка «＋ Добавить практику» на
вкладке — завести полностью свою область («Мобильное тестирование», «Локализация» и
т.п.) со своими пятью уровнями. Своя практика не участвует в расчёте Quality Gates
(их условия жёстко завязаны на id встроенных практик) и не может ни от кого зависеть
через `blockedBy` — эту связь при необходимости прописывают вручную в файле.

### Quality Gates — три ступени зрелости

Не одна практика, а контрольная точка: набор условий по нескольким практикам и
сервисам сразу, выполнение **всех** которых означает, что команда фактически перешла
на новый уровень зрелости. Проходятся по порядку.

1. **Gate 1 — Базовый контроль качества.** Релиз стал предсказуемым: дефекты
   прослеживаются, критические сценарии под контролем, а не «протестировали и
   понадеялись».
2. **Gate 2 — Автоматизированный контроль в CI/CD.** Обратная связь по сборке
   приходит без ручных действий, несоответствие условиям блокирует слияние само.
3. **Gate 3 — Устойчивое качество.** Качество не требует героизма: процессы
   самоподдерживаются, покрытие рисков и стабильность тестов держатся на целевых
   уровнях без ручного дожима перед каждым релизом.

Процент прохождения ступени = доля выполненных условий; полный список условий
каждого гейта — в интерфейсе (карточка гейта разворачивается кликом).

### Risk-Based Coverage — покрытие по риску, а не по числу тестов

У каждой фичи каждого сервиса — две оценки от 1 до 5:

- **Impact** — насколько больно бизнесу, если эта фича сломается (5 = бизнес встал);
- **Frequency** — как часто ей пользуются (5 = каждый пользователь каждый день).

`Risk Score = Impact × Frequency`, и он определяет, какого покрытия достаточно:

| Score | Зона | Чего достаточно |
|-------|------|-----------|
| 20–25 | Critical | Smoke + Sanity + Regression, и это стоит автоматизировать |
| 12–19 | High | Smoke + ключевой Sanity |
| 6–11  | Core | Smoke + выборочные кейсы |
| 1–5   | Low | чек-лист / ручная проверка |

**Правило стабильности:** если фича ещё активно переписывается каждый спринт —
автотест на неё писать рано, это `stable: false`, и инструмент сознательно уводит
такую фичу в чек-листы, а не в долг по автоматизации.

Итоговый «% покрытия рисков», который виден в шапке и на карте продукта, взвешен по
Score — то есть закрытая критичная фича значит для процента больше, чем десять
закрытых низкорисковых.

### Реестр рисков проекта

Отдельная вкладка для рисков, которые не укладываются в лестницу зрелости практик:
«единственный QA на весь проект», «внешний провайдер данных доступен только в
проде», «требования устаревают быстрее, чем кейсы». По каждому риску —
`Impact × Likelihood` (1–5 каждый), план митигации, ответственный и статус (`open` /
`mitigating` / `accepted` / `closed`). Открытые риски со score ≥ 15 автоматически
попадают в панель предупреждений наверху.

### Готовность к релизу

Пред-полётный чек-лист под конкретный релиз, а не общее состояние проекта.

- **Состав релиза** — какие сервисы в него входят (пусто = весь проект). Все сигналы
  ниже считаются только по этому составу, а не по всему, что вообще есть в файле.
- **Сигналы из данных** — не блокируют жёстко, а подсвечивают риск: критичные фичи
  этого релиза без автотестов, сервисы с flaky ≥ 5%, сервисы без smoke-покрытия,
  открытые критические риски проекта, покрытие рисков ниже 60%. Если сигнал сработал
  и решение осознанно всё равно ехать в релиз — жмёшь «принять» (в следующем релизе
  сигнал снова активен).
- **Чек-лист релиза**, по группам: тестирование релиз-кандидата → дефекты → данные и
  совместимость → выкатка и откат → после выката (это уже не блокирует, просто
  напоминание). У каждого пункта три состояния — ☐ не сделано · ☑ готово · ⊘ не
  требуется для этого релиза — и поле для заметки (ссылка на баг, оговорка). Пункты
  можно добавлять, переформулировать и удалять под специфику проекта; кнопка
  «Стандартный список» в любой момент возвращает список по умолчанию.
- **Вердикт** сверху: «готов» / «N незакрытых пунктов чек-листа» (это жёсткий стоп) /
  «пройден, но N сигналов оставлены без реакции» (это мягкое предупреждение, решение
  всё равно за человеком). Кнопка «Начать новый релиз» снимает все отметки и принятые
  сигналы и ставит новую дату — история не считается, это рабочий чек-лист, а не лог.

### Что считается автоматически

Всё производное — проценты по Quality Gates, покрытие рисков, роадмап «Сейчас /
Дальше / Потом», тренд, ROI-метрики и метрики на языке бизнеса, предупреждения об
антипаттернах — вычисляется из того, что уже введено в `quality-state.yml`. Руками
вводятся только факты и оценки (уровень практики, Impact/Frequency фичи, статус
чек-листа); ничего не дублируется вручную в двух местах.

### Импорт данных, чтобы не заводить всё руками

- **OpenAPI / Swagger → фичи сервиса.** В карточке сервиса → «Фичи» → «Импорт из
  OpenAPI». Спеку можно взять по ссылке из поля «Требования» (`specUrl`), из файла
  или вставкой текста (JSON или YAML, кодировка определяется автоматически).
  Инструмент показывает список операций (`METHOD /path` + summary) по тегам —
  отмечаешь нужные, они заводятся фичами с оценками Impact/Frequency по умолчанию
  (дальше их поправить руками), уже существующие фичи отмечены и не дублируются.
  Сам файл спеки нигде не сохраняется, берётся только список операций.
- **TMS → счётчики кейсов.** Ручной CSV/XLSX-экспорт из любой Test Management System —
  Test IT, TestRail, Jira (Xray/Zephyr), Allure TestOps и т.п. — импортёр не привязан
  к конкретной системе, разбирает обычную табличную выгрузку. Кейсы должны быть
  помечены тегами `smoke` / `sanity` / `regress` (слой — по вхождению в текст тега
  или раздела; кейс без такого тега уходит в Regression) и опционально `авто` /
  `manual` (статус автоматизации — тогда заодно посчитается и «автоматизировано»).
  В карточке сервиса → «Тестирование» → «Импорт кейсов из TMS»: выбираешь файл,
  подтверждаешь или поправляешь угаданные колонки, видишь дифф «было a/t → станет
  a/t» по каждому слою и применяешь. Слой, для которого в выгрузке ничего не нашлось,
  не трогается — не затирает то, что уже было. Тот же самый разбор доступен и из
  командной строки: `python tools/import_tms.py --file cases.csv --service <id>`.
  Flakiness % — отдельное поле рядом, вносится вручную (в выгрузках TMS обычно нет
  истории повторных прогонов, откуда это можно было бы посчитать).

## Вкладки интерфейса

Сверху — общая шапка (не вкладка, видна всегда): средний уровень зрелости практик,
% покрытия рисков, счётчик закрытых критических зон, общий прогресс, плитки бизнес-
метрик (ROI автоматизации, экономия часов ручного регресса, время до обратной связи
по smoke, предотвращённые P1/P2) и сворачиваемая панель **предупреждений** —
автоматически найденные антипаттерны (критичная дыра в покрытии, flaky выше 5%,
автотест на нестабильной фиче, сервис без ответственного, bus factor на одном QA,
критичный асинхронный сервис без контрактных тестов и т.п.). Порядок вкладок ниже —
дефолтный; свой порядок настраивается кнопкой «⋮⋮» рядом с вкладками (стрелками или
перетаскиванием).

1. **Практики** — 10 (и сколько угодно своих) карточек областей зрелости с уровнями
   L0–L4, целевыми уровнями и статусом трёх Quality Gates. Главный экран для вопроса
   «где мы вообще находимся как команда».
2. **Сервисы** — таблица всех сервисов проекта: владельцы (QA/dev/аналитик),
   жизненный цикл, здоровье, flaky %, unit/integration/contract покрытие, счётчики
   кейсов по слоям. Клик по строке открывает карточку сервиса — там же фичи с
   риск-оценкой, импорт из OpenAPI и TMS, ссылка на отчёт нагрузочного тестирования.
3. **Матрица рисков** — все фичи всех сервисов на сетке 5×5 (Impact × Frequency):
   визуально сразу видно, где скопились непокрытые точки в критичной зоне (верхний
   правый угол) — это и есть приоритет для тестирования, а не ощущение «где-то
   что-то не проверено».
4. **Риски проекта** — реестр рисков вне лестницы зрелости (см. выше): организационные,
   инфраструктурные, процессные. С митигацией, ответственным и статусом.
5. **Карта продукта** — интерактивная схема: сервисы (цвет = зона по покрытию риска)
   и инфраструктура (брокеры, БД, кеши, внешние API), связаны стрелками синхронных
   вызовов и асинхронных интеграций через инфраструктуру. Узлы можно перетаскивать,
   клик открывает карточку сервиса или инфраструктуры. Полезно, чтобы за пять секунд
   понять, что вообще в проекте есть и как оно связано — особенно новому человеку.
6. **Роадмап** — три колонки «Сейчас / Дальше / Позже», автоматически собранные из
   некрытых рисковых фич и недостигнутых целей по практикам, отсортированные по
   Risk Score. Нестабильные фичи (`stable: false`) и практики с неснятыми блокерами
   уходят в «Позже» сами — не нужно вручную решать очерёдность.
7. **Релиз** — готовность конкретного релиз-кандидата (описана подробно выше):
   состав, сигналы, чек-лист, вердикт.
8. **Тренд** — график по снапшотам истории (кнопка «＋ Снапшот» после каждого
   спринта): средний уровень зрелости, прогресс, добавленные тесты, flakiness,
   утёкшие в прод P1. Один график вместо пересказа «как у нас дела» на ретро.

## Формат `quality-state.yml`


## Устройство

```
run.py            запуск: локальный сервер + открыть браузер
build.py          сборка автономного dist/pult.html с вшитыми данными (read-only)
pyproject.toml    конфиг ruff (линтер) и метаданные пакета

pult/              бэкенд — только stdlib, без внешних зависимостей на рантайме
  __init__.py      описание пакета
  server.py        http.server (stdlib) — отдаёт UI и JSON API поверх yml,
                    проверка Origin на PUT/POST (см. докстринг файла)
  core.py          чтение/запись quality-state.yml (+ .bak при каждой записи)
  yamlio.py        минимальный YAML без зависимостей (компактный, диффабельный;
                    PyYAML подхватывается вместо него, если установлен)
  textenc.py        определение кодировки файлов (utf-8 / cp1251 / …) для импортёров
  openapi.py        разбор OpenAPI/Swagger → список операций (для импорта в фичи)
  tmsio.py           разбор CSV/XLSX-выгрузки TMS → таблица + маппинг колонок

tools/
  import_tms.py    CLI-обёртка импортёра TMS (без браузера)

web/
  index.html       весь интерфейс: один файл, ванильный JS, без сборки и фреймворков

examples/
  quality-state.example.yml   заполненный пример проекта

data/              локальные данные конкретного проекта (в .gitignore, не в репозитории)
```

API, которое отдаёт `server.py`: `GET /api/state` (текущее состояние, JSON),
`PUT /api/state` (сохранить, полная перезапись файла), `GET /api/yaml` (сырой
YAML-файл как текст), `POST /api/openapi` и `POST /api/tms` (импортёры, см. выше).
Сервер держит один локальный YAML-файл, без базы и без миграций — «сохранить» значит
«переписать файл целиком» (со свежим `.bak` перед этим).

Линт: `python -m pip install ruff && python -m ruff check .` (ruff — только для
разработки, в рантайме не нужен).

## Конфиденциальность

Инструмент ничего не отправляет наружу и не имеет ни аккаунта, ни облака, ни
телеметрии. Единственное сетевое обращение, которое он вообще умеет делать —
скачивание OpenAPI-спеки по ссылке, которую ты сам явно даёшь в импорте, и то это
делается по прямому запросу пользователя, а не само по себе.

`quality-state.yml` содержит только то, что ты в него внёс, и лежит там, куда ты
указал `--file` — по умолчанию в `data/`, которая в `.gitignore` и не попадает в
репозиторий. Сервер слушает только `127.0.0.1` и не проверяет пароль — он рассчитан
на один локальный браузер того, кто его запустил; сверка заголовка `Origin` защищает
только от чужих веб-страниц, тайком дёргающих API из твоего браузера (CSRF), это не
замена авторизации. Код инструмента можно держать открытым (например, в публичном
GitHub-репозитории) — в нём нет ничьих данных о проектах; свои реальные данные держи
отдельно, в приватном месте под доступами своей компании.
