# Пульт качества

Локальный дашборд состояния тест-фундамента проекта. Один QA / тимлид приходит на
проект, проходит по чек-листу «это есть — это есть — этого нет», и получает картину:
где качество в норме, где дыры, что делать дальше и в каком порядке, как это двигается
во времени и как объяснить ценность бизнесу.

Инструмент **локальный и ручной**: данные лежат в одном файле `quality-state.yml`,
редактируются через веб-интерфейс, никаких внешних сервисов и интеграций не требуется.

---

## Быстрый старт

```bash
python run.py
```

Откроется браузер на `http://127.0.0.1:7842`. Пока своего файла нет — показывается
демо-пример; как только что-нибудь поменяешь, рядом создаётся `data/quality-state.yml`.

Чтобы начать с нуля по своему проекту: нижняя панель → «Открыть quality-state.yml» →
«Начать с чистого листа». Сотрёт демо-сервисы, риски, карту, тренд и готовность к
релизу, уровни практик обнулит в L0; каркас 10 практик и целевые уровни останутся,
имя компании тоже. Прежняя версия файла — в `.bak`.

Свой реальный файл держи отдельно (не в этой папке — тут может быть конфиденциальная
информация о сервисах компании):

```bash
python run.py --file "C:/work/qa-state/quality-state.yml"
python run.py --port 8000 --no-browser
```

Требования: **Python 3.9+**, больше ничего. `PyYAML` подхватится автоматически, если
установлен (`python -m pip install pyyaml`) — тогда чтение файла устойчивее к ручным
правкам, но и без него всё работает.

### Показать команде / менеджеру

```bash
python build.py           # data/quality-state.yml  →  dist/pult.html
python build.py --file "C:/work/qa-state/quality-state.yml" --out report.html
```

`dist/pult.html` — самодостаточный файл с вшитыми данными, открывается двойным кликом,
работает без сервера, read-only. Его можно приложить в Confluence, положить на сетевой
диск или выложить на внутренний хостинг за SSO.

## Модель оценки

Состоит из двух уровней: **практики** (как работает команда — одно на весь проект) и
**сервисы** (что покрыто — своё у каждого сервиса, внутри — фичи с оценкой риска).

### Практики — 8 областей, уровень зрелости 0–4

| id | Область | Что оцениваем |
|----|---------|---------------|
| `process`   | Процесс и Dev-QA Sync | когда подключается QA, DoD/DoR, ревью тест-артефактов |
| `env`       | Тестовые окружения | стабильность, доступность, локальный подъём, эфемерность |
| `framework` | Автофреймворк | слои, параллельный прогон, отчётность, фабрики данных |
| `gate`      | CI / Quality Gate + Fail Fast | тесты на PR, блокировка мёржа, остановка конвейера |
| `bugs`      | Баг-процесс | единый регламент, severity, триаж, метрики утечки в прод |
| `testdata`  | Тестовые данные | генерация, изоляция между тестами, очистка |
| `reporting` | Прозрачность и отчётность | таблица покрытия, снапшоты, регулярный отчёт с ROI |
| `nonfunc`   | Нефункциональное / нагрузка | перф, security, устойчивость |
| `requirements` | Требования и критерии приёмки | где живут, есть ли DoR, трассировка требование → кейс → тест |
| `observability` | Прод: наблюдаемость и инциденты | мониторинг, алерты, синтетика, разбор P1 |

Уровни (общая шкала, детали — в интерфейсе по клику на карточку):

- **L0** — нет / хаос
- **L1** — начальный, ad hoc
- **L2** — систематизировано, вручную
- **L3** — автоматизировано, в CI, есть метрики
- **L4** — самоподдерживается, тренды, предиктивно

У каждой практики есть **целевой уровень** — куда идём на этом проекте (не всегда L4).

### Quality Gates — ступени зрелости

Контрольные точки: набор условий, выполнение которых **вместе** означает переход
команды на новый уровень. Проходятся последовательно.

1. **Gate 1 — Базовый контроль качества.** Предсказуемость релиза, прослеживаемость
   дефектов, критические сценарии под контролем.
2. **Gate 2 — Автоматизированный контроль в CI/CD.** Обратная связь по сборке
   автоматически, несоответствие блокирует слияние.
3. **Gate 3 — Устойчивое качество.** Качество поддерживается процессами, покрытие
   рисков и стабильность тестов на целевых уровнях.

Процент ступени = доля выполненных условий. Полный список условий — в интерфейсе.

### Risk-Based Coverage — покрытие по рискам, не по числу тестов

Каждая фича сервиса получает две оценки 1–5:

- **Impact** — насколько больно бизнесу, если сломается (5 = бизнес встал);
- **Frequency** — как часто этим пользуются (5 = каждый юзер каждый день).

`Risk Score = Impact × Frequency`. Зоны:

| Score | Зона | Что нужно |
|-------|------|-----------|
| 20–25 | Critical | Smoke + Sanity + Regression, автоматизировать |
| 12–19 | High | Smoke + ключевой Sanity |
| 6–11  | Core | Smoke + выборочные кейсы |
| 1–5   | Low | чек-лист / ручное |

**Правило стабильности:** если фича ещё переписывается каждый спринт — автотест писать
рано, помечай `stable: false`, инструмент уводит её в чек-листы.

«Покрытие рисков %» = покрытие, взвешенное по Score (не по количеству тестов).

### Реестр рисков проекта

Отдельная вкладка для рисков, которые не ложатся в лестницу зрелости: «единственный QA»,
«внешний провайдер только в проде», «требования устаревают быстрее кейсов». По каждому:
`Impact × Likelihood` (1–5), митигация, ответственный, статус (`open` / `mitigating` /
`accepted` / `closed`). Открытые критические (Score ≥ 15) попадают в предупреждения.

### Готовность к релизу

Отдельная вкладка — пред-полётный чек-лист под конкретный релиз.

**Состав релиза** — какие сервисы выкатываются (пусто = весь проект). Сигналы ниже
считаются по этому составу.

**Сигналы из данных** — не блокируют жёстко, а подсвечивают риск: критичные фичи
релиза без автотестов, сервисы с flaky ≥ 5%, сервисы без smoke, открытые критические
риски проекта, покрытие рисков ниже 60%. Если сработало и ты осознанно идёшь на
релиз — «принять» (сбрасывается в новом релизе).

**Чек-лист релиза** — по группам: тестирование релиз-кандидата, дефекты, данные и
совместимость, выкатка и откат, после выката (напоминание, не блокирует). У каждого
пункта три состояния — ☐ не сделано · ☑ готово · ⊘ не требуется для этого релиза —
и заметка (ссылка на баг, оговорка). Пункты можно добавлять, править, удалять;
«Стандартный список» возвращает список по умолчанию.

**Вердикт**: «готов» / число незакрытых пунктов чек-листа (жёстко) / «пройден, но N
сигналов без реакции» (мягко). «Начать новый релиз» снимает отметки и принятые
сигналы, ставит дату. Всё лежит в `quality-state.yml` → `release: {label, services,
acks, checklist}`.

### Что считается автоматически

Всё производное — статус Quality Gates, покрытие рисков, роадмап «Сейчас / Дальше /
Потом», тренд, ROI, метрики на языке бизнеса, предупреждения об антипаттернах —
вычисляется из ответов в `quality-state.yml`. Руками вводишь только факты и оценки.

### Импорт данных

Чтобы не заводить всё вручную:

- **OpenAPI / Swagger → фичи.** В карточке сервиса → «Фичи» → «Импорт из OpenAPI».
  Спеку берёт по ссылке из поля «Требования» (`specUrl`), из файла или вставки текста
  (JSON или YAML, любая кодировка). Показывает список операций (`METHOD /path` + summary),
  сгруппированный по тегам; отмечаешь нужные — они заводятся фичами с Impact/Frequency по
  умолчанию, уже существующие помечены. Файл спеки нигде не сохраняется.

- **TMS → счётчики кейсов (`t`, всего).** Ручной CSV/XLSX-экспорт из любой TMS — Test IT,
  TestRail, Jira (Xray/Zephyr), Allure TestOps и т.п. — не привязано к конкретной
  системе. Кейсы должны быть помечены тегами: `smoke` / `sanity` / `regress` — слой
  (по вхождению в текст тега/раздела; без тега уходит в Regression), `авто` / `manual` —
  статус автоматизации (необязательно, тогда заодно посчитает и `a`). В карточке
  сервиса → «Тестирование» → «Импорт кейсов из TMS»: выбираешь файл, подтверждаешь
  (или меняешь угаданные) колонки. Дифф «было a/t → станет a/t» — применяешь. Слой без
  строк в выгрузке не трогаем — не затираем то, что уже есть. Тот же разбор —
  `python tools/import_tms.py --file cases.csv --service <id>`.
  Flaky % — руками, отдельное поле рядом.

## Формат `quality-state.yml`

```yaml
company: {name: acme, updated: "2026-09-10"}   # updated проставляется автоматически

project:                                        # входные данные для ROI и DORA
  manualRunHours: 40        # ручной прогон регресса, часов
  releasesPerMonth: 2
  rate: 30                  # ставка тестировщика, $/ч
  autoHours: 80             # оценка часов на автоматизацию
  coveredShare: null        # % регресса под автотестами (null = взять из данных)
  qaInvolvement: 15         # % времени спринта на QA (бенчмарк — 30)
  p1prevented: 4            # предотвращённых P1/P2 за квартал

practices:
  - {id: process, level: 1, target: 3, note: "..."}
  # ... 8 штук по id из таблицы выше

services:
  - id: checkout
    name: checkout
    url: checkout.acme.internal
    repo: acme/checkout
    specUrl: "https://wiki/checkout"   # ссылка на требования (не сам текст)
    lifecycle: active         # dev | active | maintenance | deprecated
    health: up                # up | degraded | down | unknown
    phase: stabilize           # этап внедрения тестов: launch | stabilize | scale
    flaky: 9                    # % нестабильных тестов
    unitCov: 62                # unit-покрытие, %
    integration: partial       # интеграционные тесты: none | partial | full
    contract: none             # контрактные тесты: none | full
    perf:                      # нагрузочное тестирование — указатель на отчёт, не дублируем цифры
      link: "https://confluence/nt-checkout"  # ссылка на отчёт (JMeter/Grafana/Confluence)
      tested: "2026-08-20"      # дата последнего нагрузочного теста
      summary: "потолок ~15 RPS, ошибки после 300 потоков"  # вывод своими словами
    owners:
      qa:      {name: "В. Смирнов", email: v.smirnov@acme.io}
      dev:     {name: "М. Орлова",  email: m.orlova@acme.io}
      analyst: {name: "Д. Волков",  email: d.volkov@acme.io}
    cases:                      # счётчики: всего / автоматизировано
      smoke:   {t: 5,  a: 5}
      sanity:  {t: 14, a: 7}
      regress: {t: 22, a: 4}
    features:
      - {name: "Корзина",   impact: 4, frequency: 4, cover: automated, stable: true}
      - {name: "Промокоды", impact: 3, frequency: 2, cover: cases,     stable: true}
      # cover: none | checklist | cases | automated

infrastructure:               # брокеры, БД, кеши, внешние API
  - {id: kafka, name: Kafka, kind: broker}   # broker | db | cache | external

integrations:                 # прямые синхронные вызовы сервис → сервис
  - [gateway, checkout, rest]  # rest | grpc | graphql

infra_links:                  # сервис → инфраструктура
  - [checkout, kafka, "produce: orders.created"]
# добавляется в карточке сервиса → «Интеграции» → «＋ Добавить интеграцию»:
# форма с выбором «вызов сервиса» (цель + протокол) или «через инфраструктуру»
# (узел + что делает + детали). Новый узел инфры создаётся там же.
# Узлы инфры редактируются/удаляются кликом по ним на карте компании.

map_pos: {}                   # позиции узлов на карте (авто, если пусто)

risks:                        # проектные риски вне лестницы зрелости
  - id: r1
    title: "Единственный QA на всех сервисах — bus factor"
    impact: 5                  # ущерб если реализуется (1–5)
    likelihood: 3              # вероятность (1–5)
    mitigation: "дока по передаче, раздать доступы"
    owner: "тимлид"
    status: open               # open | mitigating | accepted | closed

release:                      # готовность к релизу (вкладка «Релиз»)
  label: "2026-09-10"         # свободная метка релиза
  services: [checkout, orders] # состав; пусто = весь проект (все активные сервисы)
  acks: {flaky: true}         # принятые сигналы (id → true)
  checklist:                  # пункты чек-листа; state: "" | ok | na
    - {id: smoke, group: test, text: "Smoke затронутых сервисов — 100% зелёный", state: ok, note: ""}
    # group: test | defects | data | ship | after

history:                      # снапшоты для тренда — кнопка «＋ Снапшот» после спринта
  - {d: "S14 · 9 сен", iso: "2026-09-09", s: 1.4, prog: 38, added: 15, flaky: 4, p1: 0}
```

Модель (описания уровней L0–L4, условия Quality Gates, пороги) живёт в коде интерфейса,
а не в файле — файл содержит только ответы по конкретному проекту.

Полный заполненный пример: [`examples/quality-state.example.yml`](examples/quality-state.example.yml).

## Устройство

```
run.py        запуск: локальный сервер + открыть браузер
server.py     http.server (stdlib) — отдаёт UI и JSON API поверх yml
core.py       чтение/запись quality-state.yml (+ .bak при каждой записи)
yamlio.py     минимальный YAML без зависимостей (компактный, диффабельный)
textenc.py    определение кодировки файлов (utf-8 / cp1251 / …) для импортёров
openapi.py    разбор OpenAPI/Swagger → список операций (для импорта в фичи)
tmsio.py      разбор CSV/XLSX-выгрузки TMS → таблица + маппинг колонок
build.py      сборка автономного dist/pult.html с вшитыми данными
tools/        CLI-обёртка импортёра (import_tms.py)
web/index.html  весь интерфейс (один файл, ванильный JS)
examples/     заполненный пример
data/         локальные данные (в .gitignore)
```

API: `GET /api/state` (JSON), `PUT /api/state` (сохранить), `GET /api/yaml` (сырой файл),
`POST /api/openapi` / `/api/tms` (импортёры, см. выше).

с компанией (CI, хостинг), — потом.

## Конфиденциальность

Инструмент ничего не отправляет наружу. `quality-state.yml` содержит только то, что ты
в него внёс, и лежит там, куда ты укажешь `--file`. Код инструмента можно держать
открытым; свои данные — в приватном месте под доступами компании.
